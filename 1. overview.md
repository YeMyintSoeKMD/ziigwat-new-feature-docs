# ZiiGwat POS — Serialized Inventory / IMEI & Serial Tracking

## Technical Requirement Specification

**Project:** ZiiGwat POS
**Feature:** Serialized Inventory / IMEI / Serial Number Tracking
**Purpose:** Extend the existing inventory system to support tracking of individual physical devices such as phones, tablets, laptops, electronics, and other serialized products.

---

# 1. Background

ZiiGwat POS currently manages inventory mainly using quantity-based stock.

Example:

- iPhone 15 Pro — 5 units
- USB Cable — 20 units
- Keyboard — 10 units

For normal products, quantity tracking is sufficient.

However, phone shops and electronics shops require tracking of individual physical devices using identifiers such as:

- IMEI 1
- IMEI 2
- Serial Number
- EID
- Device Number
- Other custom identifiers

The system must therefore support both:

1. Quantity-based inventory
2. Serialized inventory

The existing quantity-based inventory must continue to work without being replaced.

---

# 2. Main Objective

Implement serialized inventory tracking as an additional inventory layer.

The system must be able to answer questions such as:

- Which IMEI is currently in stock?
- Which location currently has the device?
- Which supplier did the device come from?
- What was the purchase cost of this specific device?
- What is the asking price of this specific device?
- Which customer bought this device?
- Which order sold it?
- Was the device returned?
- Was it transferred between branches?
- Was it damaged, lost, or repaired?
- What is the complete history of this IMEI?

---

# 3. Existing Inventory System

The current inventory architecture contains concepts similar to:

```text
items
    ↓
stocks
    ↓
stock_transactions
```

`stocks` stores the current aggregate stock quantity.

Example:

```text
iPhone 15 Pro
Yangon Branch
Balance = 5
```

`stock_transactions` records quantity movements such as:

- Purchase
- Sale
- Sale Return
- Purchase Return
- Adjustment
- Transfer
- Wastage
- Loss
- Opening Stock

This system must remain.

---

# 4. New Serialized Inventory Architecture

Serialized inventory will add another layer:

```text
items
    │
    └── inventory_units
            │
            ├── inventory_unit_identifiers
            ├── inventory_unit_attributes
            └── inventory_unit_movements
```

The full design becomes:

```text
QUANTITY INVENTORY

items
 ├── stocks
 └── stock_transactions


SERIALIZED INVENTORY

items
 └── inventory_units
      ├── inventory_unit_identifiers
      ├── inventory_unit_attributes
      └── inventory_unit_movements
```

For serialized items, both systems must remain synchronized.

---

# 5. Inventory Tracking Types

Each item must have an inventory tracking mode.

Supported modes:

```text
quantity
serialized
```

### Quantity

Existing behavior.

Examples:

- Drinks
- Rice
- Cables
- Accessories
- General merchandise

### Serialized

Every physical unit must be registered individually.

Examples:

- Mobile phones
- Laptops
- Tablets
- Cameras
- Smart watches
- Secondhand electronic devices

---

# 6. Important Design Principle

Do NOT create tracking modes such as:

```text
imei
serial
device_number
```

A physical device may contain multiple identifiers.

Example:

```text
iPhone

IMEI 1
IMEI 2
Serial Number
EID
```

Therefore the item is simply:

```text
inventory_tracking = serialized
```

The identifiers are stored separately.

# 10. Inventory Unit Identifiers

Identifiers must be stored separately from the physical inventory unit.

Recommended table:

## `inventory_unit_identifiers`

| Field             | Purpose                                  |
| ----------------- | ---------------------------------------- |
| id                | Primary key                              |
| shop_id           | Shop                                     |
| inventory_unit_id | Physical device                          |
| identifier_type   | imei / serial / eid / device_no / custom |
| slot              | Identifier slot                          |
| value             | Original value                           |
| normalized_value  | Normalized search value                  |
| is_primary        | Main identifier                          |

Example:

| Unit | Type   | Slot | Value           |
| ---- | ------ | ---: | --------------- |
| 101  | IMEI   |    1 | 351234567890001 |
| 101  | IMEI   |    2 | 351234567890019 |
| 101  | Serial |    - | ABC123XYZ       |
| 101  | EID    |    - | 89049...        |

IMEI must be stored as text/string.

Do not store IMEI as an integer.

---

# 11. Identifier Validation

IMEI should normally be validated using:

- 15 digits
- No letters
- Normalize spaces/hyphens
- Luhn checksum where applicable
- Unique within the shop

Example:

```text
351 234-567 890 001
```

should normalize to:

```text
351234567890001
```

Serial numbers may have different validation rules.

Custom identifiers should not automatically use IMEI validation.

The current default product price remains in:


Pricing priority:

```text

```

Example:

```text

Unit A
asking_price = null
```

This is required mainly for:

- Secondhand phones
- Refurbished phones
- Different conditions

# 18. Purchase Workflow

When purchasing a serialized product:

Example:

```text
Purchase

iPhone 15 Pro
Quantity = 3
```

The system must require three physical device records.

```text
Purchase Detail
Quantity = 3

↓ creates

Inventory Unit A
Inventory Unit B
Inventory Unit C
```

For each unit, the user enters/scans identifiers.

Example:

```text
Unit A
IMEI 001
Serial A

Unit B
IMEI 002
Serial B

Unit C
IMEI 003
Serial C
```

The number of inventory units must equal the purchased quantity.

Serialized items cannot use fractional physical quantity.

Invalid example:

```text
1.5 phones
```

---

# 19. Purchase Transaction Requirements

Serialized purchase should:

1. Create purchase.
2. Create purchase detail.
3. Validate serialized units.
4. Validate required identifiers.
5. Validate identifier uniqueness.
6. Create inventory units.
7. Create identifiers.
8. Create optional attributes.
9. Increase aggregate stock.
10. Create stock transaction.
11. Create unit movement history.
12. Commit all changes.

All steps must run inside the same database transaction.

If any step fails, the whole operation must rollback.

# 20. POS / Sale Workflow

When cashier selects a serialized item, the POS should require selection or scanning of the exact available unit.

Example display:

| IMEI   | Condition | Asking Price |
| ------ | --------- | -----------: |
| ...001 | New       |    3,000,000 |
| ...002 | Used A    |    2,500,000 |
| ...003 | Used B    |    2,200,000 |

Cashier may select or scan:

```text
IMEI ...002
```

System must validate:

- Correct shop
- Correct item
- Correct location
- Status is `in_stock`
- Unit has not already been selected
- Unit has not already been sold

Then:

```text
inventory_unit.status
in_stock → sold
```

Aggregate stock decreases by 1.

Movement history is created.

---

# 21. Concurrent Sale Protection

The same IMEI must never be sold twice.

Example:

Cashier A selects:

```text
IMEI 001
```

At the same time Cashier B attempts:

```text
IMEI 001
```

Only one sale must succeed.

Use database transactions and row locking where appropriate.

---




# 32. Reconciliation Requirement

For serialized products, the system should be able to compare:

```text
stocks.balance_quantity
```

against:

```text
physical inventory unit count
```

Example:

```text
Stock Balance = 10
Physical Units = 9
```

System should report:

```text
Inventory discrepancy detected.
```

Do not silently auto-correct discrepancies.

# 33. Multi-Shop / Tenant Security

ZiiGwat POS is a multi-shop system.

Every serialized inventory query must respect:

```text
shop_id
```

Shop A must never be able to:

- Search Shop B IMEI
- View Shop B devices
- Sell Shop B device
- Transfer Shop B device
- Return Shop B device
- Modify Shop B device

Server-side validation is required.

Do not rely only on frontend filtering.

---

# 34. Location Security

A device may only be sold from its current location unless there is an explicit existing business rule allowing otherwise.

Example:

```text
IMEI 001

Current Location:
Yangon
```

Mandalay POS must not sell the device.

It must first be transferred properly.

- Serialized purchase

- Stock transfer
- Stock adjustment
- Loss

# 37. Existing Stock Conversion

If an existing product currently has:

```text
Stock = 20
```

the user must not simply change:

```text
quantity → serialized
```

without registering the physical devices.

The safe behavior is either:

1. Prevent conversion while stock exists.

or

2. Provide an onboarding process requiring exactly 20 physical units to be registered.

Example:

```text
Existing Quantity = 20

Required:
20 IMEI / Serial units
```

Only then activate serialized tracking.

For the initial implementation, blocking conversion when existing stock exists is acceptable and safer.

# 39. Core Business Rules

The following rules are mandatory.

### Rule 1

IMEI and Serial Numbers identify physical devices.

They are not product records.

### Rule 2

One physical serialized device = one `inventory_unit`.

### Rule 3

One physical serialized sale = one `order_detail`.

### Rule 4

Serialized sale quantity must be `1`.

### Rule 5

Serialized order detail must reference an `inventory_unit`.

### Rule 6

Sale return must reference the exact device originally sold.

### Rule 7

Purchase return must identify the exact unit returned.

### Rule 8

Stock transfer must identify exact serialized units.

### Rule 9

Transfer is a movement, not a device status.

### Rule 10

Sale return is a movement, not a device status.

### Rule 11

Default price belongs to `item_prices`.

### Rule 12

Device-specific asking price belongs to `inventory_units`.

### Rule 13

Final historical selling price belongs to the sale/order detail.

### Rule 14

Color/storage/RAM should normally use product variants.

### Rule 15

Condition and device-specific value belong to the inventory unit.

### Rule 16

Aggregate stock and serialized units must always remain synchronized.

### Rule 17

Every operation must respect shop and location ownership.
